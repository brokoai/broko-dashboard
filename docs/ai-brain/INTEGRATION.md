# AI Brain: persistence and dashboard integration (stage 2)

Scope of this stage: put the Communication Agent inside the existing dashboard (AI Inbox with
approval), using the existing `Backend`/`Repo` interfaces, **with synthetic data only**. Nothing here
reads a mailbox, calls a language model, or touches a database. Nothing has been pushed or deployed.

## What changed in the dashboard

| Piece | Where | Notes |
| --- | --- | --- |
| Optional backend capabilities | `Repo.aiInbox?` (`view()`), `Repo.aiInboxCounts?` (`counts()`, chat), `Repo.aiInboxWriter?` (`process / requeue / review`) in `src/lib/backend/types.ts` | Independent. A backend without `aiInbox` shows "not connected"; the UI shows write controls only with `aiInboxWriter`. See `AI_INBOX_READINESS.md`. |
| Demo implementation | `src/lib/backend/demo/ai-inbox.ts`, wired in `demo/repo.ts` | Runs the sample emails through the real pipeline per request. Only the visitor's decisions are stored. |
| Task creation | Through the demo `Repo` task path (`createAiTask`) | `source = "email"`, `external_reference = synthetic-email:<n>`, creator = the reviewer. Deterministic id `ai<n>` makes approval idempotent. |
| Review action | `src/app/(app)/inbox/actions.ts`, `src/lib/ai-review-input.ts` | Authenticates first, validates input, relays to the backend. Reviewer identity comes from the session only. |
| UI | `src/app/(app)/inbox/page.tsx`, `src/components/ai-inbox-list.tsx` | Existing components, responsive, labelled "Synthetic". Admin-only. |
| Supabase backend | unchanged | Has no `aiInbox`, so the real backend shows "not connected" rather than pretending. |

Approving creates one task with the demo's normal activity event (`task_created`). Rejections are stored
by index and are not shown in the activity feed (demo limitation).

## Minimum persistence required (and what each need maps to)

| Need | Minimum | Proposed in `supabase/proposed/0003_ai_brain.proposed.sql` |
| --- | --- | --- |
| Incoming message reference | sender, subject, ids, hash, no body | `ai_messages` row (excerpt NULL by default) |
| Processing job state | one status per message | `ai_messages.status`, `error` |
| Idempotency | unique key per email; unique task per email | `ai_messages.dedupe_key` primary key; partial unique index on `tasks(source, external_reference)` |
| Approval decisions | who, when, outcome | `reviewed_by`, `reviewed_at`, `status`; changed only by `ai_approve_message(p_review_id)` / `ai_reject_message(p_review_id)` (admin-checked, row-locked, addressed by the persisted `review_id`) |
| Audit events | content-free event per stage | **No new table.** Existing `activity_events` (service role writes; types already exist) |

Everything else (policy, owner rules) stays in configuration, not in tables, until Broko wants to edit them in the UI.

## Persistence contract (authoritative; proposed SQL 0003/0004, NOT APPLIED anywhere)

This section is the single reference for identifiers and RPCs a future Supabase `aiInbox` repository must follow. The
pure mapping and argument builders are in `src/lib/backend/supabase/ai-contract.ts`; they are **contract code, not a repository**,
and nothing in the app calls them yet.

### Identifiers

| Id | Where it comes from | Format | Rule |
| --- | --- | --- | --- |
| `review_id` | `ai_messages.review_id`, **generated by the database** (`default gen_random_uuid()`) | lower-case UUID | The repository INSERTs a message **without** it and always reads it back. It never derives one from `dedupe_key` (`reviewIdFor` is the in-memory demo only; a test fails if database code calls it). It is the only message id the browser sees and the only argument of approve/reject. |
| public job id | `ai_jobs.correlation_id` | 12 lower-case hex = first 12 of SHA-256(job key); `jobId(ref)` in `src/lib/ai-brain/jobs.ts` | The only job id outside the database. `JobRecord.id` and `AiJobView.id` are this value. `ai_complete_job`, `ai_retry_job`, `ai_fail_job`, `ai_requeue_job` take `p_job_id text` and match on `correlation_id`. `ai_enqueue_job` returns it. Unique, with a regex check (a collision fails closed). |
| internal job uuid | `ai_jobs.id` | uuid | Internal. Never read, sent, shown or accepted by any RPC (an uuid passed as `p_job_id` is rejected by the regex before any lookup). |
| job key | `JSON.stringify([provider, mailbox_ref, source_message_id])` = SQL `array_to_json(array[...])::text` | text | Byte-for-byte parity checked by `job_key_parity.pglite.mjs`. |

### RPCs (parameter names are exactly these; `tests/ai-supabase-contract.test.ts` compares them with the SQL text)

| Function | Parameters | Returns | Caller |
| --- | --- | --- | --- |
| `ai_enqueue_job` | `p_provider, p_mailbox_ref, p_source_message_id [, p_max_attempts]` | public job id (text) | service role |
| `ai_claim_job` | `p_worker, p_lease_seconds` | claimed row or none | service role |
| `ai_complete_job` | `p_job_id, p_worker, p_attempt, p_workflow_id, p_outcome, p_audit_failed` | boolean | service role (fenced on lease owner + attempt) |
| `ai_retry_job` | `p_job_id, p_worker, p_attempt, p_error, p_run_at, p_workflow_id, p_audit_failed` | boolean | service role (fenced; time clamped to [now, now+24 h]) |
| `ai_fail_job` | `p_job_id, p_worker, p_attempt, p_error, p_workflow_id, p_audit_failed` | boolean | service role (fenced) |
| `ai_requeue_job` | `p_job_id` | boolean | `authenticated`, administrator-checked inside; not callable by service role |
| `ai_approve_message` | `p_review_id, p_title, p_description, p_assigned_to, p_due_at, p_priority` | task uuid | `authenticated`, administrator-checked inside (admin check before "not found") |
| `ai_reject_message` | `p_review_id` | void | `authenticated`, administrator-checked inside |
| `ai_record_audit_event` | event fields + `p_metadata` | boolean | service role |

### Audit metadata

Keys are allow-listed (unchanged) and **values are now typed** inside `ai_record_audit_event` to the shape of `ActivityMetadataSchema`:
`workflow_id` 12 hex or null; `event_key` `[0-9a-z_:-]{1,120}`; `classifier_mode`, `fallback_reason`, `decision`, `actor_kind` fixed
enums; `error_category` the fixed category list; `intent` `[a-z_]{1,40}`; `outcome` `[A-Z_]{1,40}`; `flags` an array of at most 12
`[a-z_]{1,40}` strings. Anything else raises `invalid metadata value` (the value is never echoed). Approve/reject write their audit rows
inline from values the function itself produced. Verified by the PGlite SQL test and mutation run (single session only).

### Sender address

`AiMessageView.sender_email` is deliberately kept: the administrator reviewing a message must see who it claims to be from to judge
`sender_unverified` and ownership. It leaves the server only through `backend.aiInbox.view()` (administrator check) on an
administrator-only page, through the explicit allow-list in `toMessageView`. It is not in activity events or audit metadata. If
Broko prefers, replace it with the domain only; the one place to change is `view.ts` plus `ai-inbox-list.tsx`.

### What is and is not tested

* **Contract tests** (`tests/ai-supabase-contract.test.ts`, `tests/sql-security.test.ts`): hold application mapping and RPC argument
  names against the SQL **text**. No database is involved. They are not integration tests.
* **PGlite SQL tests** (`supabase/proposed/tests`): run the SQL in an in-process single-connection PostgreSQL. Real SQL semantics,
  but one session: they cannot show `FOR UPDATE SKIP LOCKED` or the approval row lock working. The harness lists those as BLIND.
* **Local two-session run (2026-10-25, throwaway harness, local PostgreSQL 18.4):** `SKIP LOCKED`, the approval row lock, 8-way races and the stale-lease fence behaved as designed. Not Supabase, and the harness is not in the repo.
* **Not done:** any run against Supabase (real roles, PostgREST, GoTrue, default privileges). See `REMOTE_VERIFICATION_CHECKLIST.md`.
* **Not built:** the Supabase `aiInbox` repository. When it is, it must use `ai-contract.ts` (a test fails otherwise) and ship with
  integration tests against a real database.

## Review of the proposed task-table guard change

0002 forces every browser-inserted task to `source = 'manual'`. Approval must create `source = 'email'`.

* **First draft rejected:** a transaction-local setting read by the guard. A security rule would depend on state
  that any SQL-capable code path in the session can set.
* **Current proposal:** make the guard `SECURITY INVOKER` and trust only inserts executed by a role other than
  `authenticated`/`anon`. Only the admin-checked `SECURITY DEFINER` approval function does that. No client-writable state is trusted.
* **Alternative considered:** the Next.js server writes with the service-role key after checking the admin in code.
  Simpler, but it moves the only authorization into application code and puts a powerful key in the web tier. Not recommended.
* **Not verified.** Four points to confirm on a disposable Supabase branch are listed in the SQL comments. No migration
  (0002 or 0003) should be applied until Broko confirms the project and owner, and this is tested there.

## Classifier modes (model integration, stage 3)

`BROKO_AI_CLASSIFIER` = `rules` (default) or `llm`. `llm` also needs `ANTHROPIC_API_KEY`; without it the inbox uses the rules
and shows a note. The active mode is always shown on the AI Inbox page, and each message records which classifier produced it.

* **Where it is chosen:** `selectClassifier()` (`src/lib/ai-brain/classifier-select.ts`), once per server process, from server-side env only.
* **Fallback:** model unreachable, non-JSON, or schema-invalid output (including attempts to name an owner or approve) -> the rule-based
  classifier, recorded as `model_unavailable` / `model_output_invalid` and shown as a badge. After an outage the model is skipped for 60 s.
* **Unchanged:** strict validation, grounding, injection tripwire, owner rules, role checks, duplicate suppression, human approval.
* **Cost control:** results are cached per message content (10 min; 60 s for fallbacks, 64 entries), the duplicate delivery is never
  classified, and non-admins cannot trigger classification. A public demo with `llm` enabled would still cost at most ~9 calls per 10 minutes per server instance; leave it `rules` there.
* **Latency:** first page load in model mode took ~9 s in development (nine calls in parallel); cached loads ~150 ms. A persistent store
  with background processing (next stage) removes this from the request path.
